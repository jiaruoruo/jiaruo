## 一、议题一：新增ASU功能需求对MCU资源的要求

### 1.1 ASIL 等级要求

**核心问题**：新增功能是否必须达到 ASIL-D？能否做 ASIL 分解？

**需要了解**：
- [ ] 新增ASU功能的安全目标（Safety Goal）是什么？HARA分析结论？
- [ ] 功能失效的后果：严重度(S)、暴露率(E)、可控性(C) 分别定级？
- [ ] 是否存在 ASIL 分解方案？
  - 例：ASIL-D 分解为 ASIL-B + ASIL-B / ASIL-C + QM？
  - 哪些子功能可以降为 QM？（诊断、舒适控制、状态上报）
- [ ] 安全机制清单：
  - 看门狗（外部独立 WDG）
  - RAM/Flash 完整性检查（ECC/CRC）
  - 时序监控（Deadline Monitor）
  - 流控（Program Flow Monitoring）
  - 冗余校验（双核交叉比较？）

**关键判断依据**：
> 空气悬架失效可能导致车身高度异常 → 影响行驶稳定性 → 严重度可能达 S2/S3  
> 但悬架通常有机械限位，可控性可能比制动/转向好

### 1.2 实时性要求

**需要了解**：
- [ ] 控制回路周期要求？
  - 气泵/电磁阀控制：多少 ms？（典型 10-50ms）
  - 高度传感器采样：多少 ms？
  - 减震器阻尼调节：多少 ms？
- [ ] 端到端延迟容忍度？（传感器→计算→执行）
- [ ] 最差执行时间（WCET）约束？
- [ ] 是否需要确定性调度（如 OSEK/AUTOSAR OS 固定优先级）？
- [ ] 实时性要求是否受车速影响？（高速工况是否需要更高频率？）

### 1.3 RAM 需求估算

**需要了解**：
- [ ] 应用层数据量：
  - 传感器缓冲区大小（高度传感器、压力传感器等）
  - 控制算法中间变量（PID/滤波器/状态机）
  - CAN/LIN 报文收发缓冲区
- [ ] 安全机制占用：
  - ASIL-D 冗余变量存储（双份变量 × 安全相关数据）
  - 栈空间（ASIL-D 任务需单独栈，MC/DC 100% 覆盖要求更大的栈余量）
  - ECC 开销（如使用 ECC RAM，有效容量约 7/8）
- [ ] RTOS 开销：
  - 任务栈（安全监控 1ms + 控制任务 + 通信任务 + 诊断任务）
  - 内核对象（信号量、消息队列、定时器）
- [ ] NVM 运行时镜像（日志、DTC 记录、标定参数）

**参考估算公式**：
```
总 RAM = 应用数据 + 安全冗余(20-30%) + RTOS开销 + 栈(5-10个任务) + NVM镜像 + 余量(20%)
```

### 1.4 Flash 需求估算

**需要了解**：
- [ ] 应用代码体积：
  - ASU 控制算法代码
  - IO 驱动代码（气泵、电磁阀、高度传感器、压力传感器等）
  - 通信协议栈（CAN/LIN 驱动 + DBC 生成代码）
- [ ] 安全机制代码：
  - 安全监控任务
  - 诊断模块（DTC 管理、UDS 服务）
  - 自检代码（启动自检 + 运行中监控）
- [ ] 标定数据（A2L 文件映射的 Flash 区域）
- [ ] 日志/事件记录区
- [ ] FOTA 分区（双分区升级需要 2× 应用镜像）
- [ ] 安全存储（Flash CRC 校验区、安全启动密钥区）

**参考估算公式**：
```
总 Flash = 应用代码 + 安全机制(15-25%) + 标定数据 + 通信栈 + FOTA双区 + 余量(20-30%)
```

### 1.5 核的需求

**需要了解**：
- [ ] 是否需要多核？还是单核够用？
  - 判断依据：控制频率 + 算法复杂度 + 安全隔离需求
- [ ] 多核方案选型：
  - 异构多核（如 A核应用 + M核实时控制）— 安全隔离天然好
  - 同构多核（双M核）— 资源复用但需软件隔离
- [ ] 安全隔离要求：
  - ASIL-D 任务和 QM 任务是否需要物理隔离（不同核 / MPU 分区）？
  - 是否需要看门狗独立（每核一个外部 WDG）？
- [ ] 核间通信需求：
  - Shared Memory（需注意缓存一致性和 MPU 保护）
  - 核间中断 / 消息传递
  - 通信频率和数据量
- [ ] 启动顺序和同步：
  - Bootloader 在哪颗核上运行？
  - 核间初始化同步机制？

### 1.6 IO 驱动需求

**需要了解**：
- [ ] 传感器 IO：
  - 高度传感器：模拟（ADC）还是数字（CAN/LIN/I2C）？几路？
  - 压力传感器：模拟还是数字？几路？
  - 温度传感器（气泵/储气罐）：模拟还是数字？
- [ ] 执行器 IO：
  - 气泵驱动：PWM 驱动？电流大小？是否需要电流反馈？
  - 电磁阀：开关型还是比例型？几路？驱动电流？
  - 减震器阻尼调节：电控（PWM/CAN）还是纯机械？
- [ ] 通信接口：
  - CAN：几路？波特率？（典型 500kbps）
  - LIN：几路？波特率？（典型 19.2kbps/20kbps）
  - 以太网：是否需要？（如果走域控制器方案可能需要）
- [ ] 诊断接口：
  - UDS over CAN（ISO 14229）
  - OBD 接口
- [ ] 特殊 IO：
  - 故障指示灯控制
  - 急停/安全切断电路

## 二、议题二：ASU软件是否可拆分解耦部署到不同的核

### 2.1 功能分解分析

**需要明确 ASU 功能模块及其依赖关系**：

| 功能模块 | 实时性 | ASIL | 是否可独立部署 |
|---------|-------|------|--------------|
| 高度控制算法 | 高 | ? | 待确认 |
| 气泵/阀门控制 | 高 | ? | 待确认 |
| 减震器阻尼控制 | 中 | ? | 待确认 |
| 传感器数据采集 | 高 | ? | 待确认 |
| 通信管理（CAN/LIN） | 中 | QM | ✅ 可独立 |
| 诊断管理 | 低 | QM | ✅ 可独立 |
| 安全监控 | 最高 | ASIL-D | ✅ 应独立 |
| 舒适/运动模式管理 | 低 | QM | ✅ 可独立 |
| 标定/Flash管理 | 低 | QM | ✅ 可独立 |

### 2.2 解耦部署方案选项

**方案 A：安全 / 非安全分离**
```
核 A（安全核）：高度控制 + 安全监控 + 传感器采集（ASIL-D/B）
核 B（应用核）：通信 + 诊断 + 模式管理 + 标定（QM）
```
- 优点：天然满足 ASIL 独立性要求
- 难点：核间通信延迟需评估

**方案 B：实时控制 / 后台分离**
```
核 A（实时核）：所有实时控制任务（高度+气泵+减震器）
核 B（后台核）：通信 + 诊断 + 安全监控 + 标定
```
- 优点：实时性有保障，后台不干扰控制
- 难点：安全监控放后台核是否满足独立性？

**方案 C：按执行器分离**
```
核 A：悬架高度控制（气泵+阀门+高度传感器）
核 B：减震器阻尼控制 + 通信 + 诊断 + 安全监控
```
- 优点：负载均衡
- 难点：功能耦合（高度和阻尼可能需要协同）

### 2.3 解耦评估矩阵

**需要和底盘同事一起评估**：

| 评估维度 | 问题 | 影响 |
|---------|------|------|
| 功能耦合度 | 高度控制和阻尼控制是否需要实时协同？ | 高耦合→难拆分 |
| 共享数据量 | 核间通信每秒传多少数据？ | 数据量大→Shared Memory带宽压力 |
| 安全独立性 | ASIL分解后能否满足独立性（独立性/独立性）？ | 不独立→不能分核 |
| 开发复杂度 | 多核调试、同步、故障处理复杂度 | 多核→开发周期+20-30% |
| 芯片成本 | 多核芯片 vs 单核芯片成本差多少？ | 成本敏感→倾向单核 |
| 功耗 | 多核待机功耗 vs 单核 | 影响整车续航 |
| 供应商支持 | 芯片厂商是否提供多核参考设计？ | 无参考设计→开发风险高 |

### 2.4 需要确认的关键依赖

- [ ] ASU 和底盘其他模块（ESP/EMS/转向）的协同频率和数据量
- [ ] 是否需要和底盘域控制器（DCU）交互？走什么协议？
- [ ] ASU 是独立 ECU 还是集成在底盘域控制器里？
- [ ] 如果集成到域控制器，和其他功能（ESP/EMS）共享 MCU 资源如何划分？
- [ ] FOTA 升级策略：ASU 软件单独升级还是和整个域控一起升级？
