很多人做 Agent 优化，第一反应是换更强的模型，调 temperature，拉长思考预算，甚至考虑微调。

LangChain 最近分享了一个很有参考性的案例：他们没有改 Nemotron 3 Ultra 的权重，也没有调整生成参数，只优化了 Agent 周围的运行环境，最终让这个开放模型的表现逼近顶级闭源模型，同时把单次运行成本降到了约十分之一。

这个案例再次证明了：**一个 Agent 的能力，不只取决于模型，也取决于模型被放进了什么样的Harness里。**

## Agent 不只是模型

LangChain 把一个 Agent 拆成两部分。

1.  1\. **模型**，负责理解、推理和决策。
2.  2\. **Harness**，也就是模型运行时所处的脚手架，包括系统提示词、工具描述、中间件、上下文注入、重试机制、调用限制等。

模型像发动机，Harness 则像底盘、方向盘和传动系统。

发动机再强，如果底盘不匹配，也跑不出该有的性能。

一个不适合模型的 Harness，可能让 Agent 出现各种看似“模型不够聪明”的问题：

-   • 已经拿到信息，却反复追问
-   • 文件只读了一页，就误以为看完了
-   • 任务还没完成，就过早结束
-   • 工具调用出错后直接放弃
-   • 在某个动作里来回循环，直到超时
-   • 长任务中丢失上下文，无法持续推进

这些问题未必需要训练模型，很多时候只需要把模型周围的运行机制调好。

## 一个开放模型，如何逼近 Opus

LangChain 选择了 NVIDIA 的 Nemotron 3 Ultra 进行实验。

他们保持模型不变，只调优 Harness，包括系统提示词、工具说明、模型调用前后的中间件、工具调用前后的中间件，以及上下文信息出现的位置与时机。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/X6nEuibEvV4RcDy7icfic1ELCiczFwmib7MLl7ZyVp58BMpEScoheuoRQ0RnibDHHUScGdp4e4RFs8XYhHVETWnElf7yNCWSla9kXpN5OeDPc02gQ/640?from=appmsg&watermark=1&tp=webp&wxfrom=5&wx_lazy=1#imgIndex=0)

生成参数则始终使用服务商推荐默认值，没有通过调 temperature、top-p 或思考预算来“刷分”。

结果是：

-   • Nemotron 3 Ultra 的典型得分，从约 **0.80** 提升到约 **0.84**
-   • 最佳运行达到 **0.86**
-   • Opus 4.8 的最佳成绩是 **0.87**
-   • Nemotron 在完整 Deep Agents 评测集上的单次成本约 **4.48 美元**
-   • Opus 的对应成本约 **43.48 美元**
-   • 延迟基本持平，单项测试中位数约 **10 秒**

也就是说，经过 Harness 调优后，Nemotron 3 Ultra 以约十分之一的成本，跑出了接近 Opus 的 Agent 任务表现。

## 不要靠感觉调 Prompt，要从评测开始

Harness 调优最容易掉进一个坑：看见一个失败案例，立刻改提示词，然后看到一次成功，就以为问题解决了。

LangChain 的做法更像训练模型，只不过训练对象不是权重，而是 Agent 的运行环境。

他们把评测集当作 Harness Engineering 的训练数据，形成一个循环：

## Agent 不只是模型

2.  1\. **评测**：让 Agent 跑整体行为测试。
3.  2\. **观察**：阅读失败任务的 trace，看它到底在哪一步偏离了正确路径。
4.  3\. **诊断**：将失败轨迹归类，例如文件读取不完整、没有正确压缩上下文、工具调用失败后无法恢复等。
5.  4\. **工程改动**：每次只做一个小而明确的修改。
6.  5\. **再次评测**：先用小规模、有代表性的样本快速筛选，再让有效改动进入更完整、更昂贵的评测。

![](https://mmbiz.qpic.cn/mmbiz_png/X6nEuibEvV4RTpVJKbaceIcdIQMr0KuN6dqHdJH9rw2kZEU7V18r6D1niciarB4tTzORosE4PbYw0Yr2d959zhvqL5VEIeseKpkIkCCbltBbM4/640?from=appmsg&watermark=1&tp=webp&wxfrom=5&wx_lazy=1#imgIndex=3)

这里有两个关键原则。

第一，**一次跑得好不代表真的变好了**。Agent 的运行带有随机性。一个改动必须在多次试验中重复产生收益，并且没有破坏其他能力，才值得保留。

第二，**不要每次都跑全量评测集**。完整评测昂贵，因此可以先用覆盖不同任务类型的小样本筛选。如果改动能在有代表性的样本上稳定生效，再扩大范围验证。

这很像产品开发中的灰度发布，也像机器学习中的训练集、验证集和测试集。

## Prompt 不是万能药

很多人做 Agent 优化，习惯先重写系统提示词。

比如不断加长规则：“你是一个严谨的 Agent”“请认真完成任务”“请不要遗漏信息”“请在行动前充分思考”“请检查自己的答案”。

但 LangChain 的经验是，这类泛化指令通常效果有限。

原因并不复杂。一个能力已经不错的模型，真正失败的地方往往不是因为它没有看到“请认真”四个字，而是因为关键信息出现得太早、太远，或者根本没有出现在它最需要的时刻。

真正有效的提示，通常很短，而且只解决一个已经在 trace 中被确认的问题。

例如，如果 Agent 完成任务后总是不明确输出最终结果，那么提示词就只针对这个行为补充一条要求。不要因为一个问题，就给系统提示词塞进十条泛泛而谈的原则。

## 同一句话，放错位置就没用

文章里最值得借鉴的案例，是关于文件读取的。

他们希望 Agent 遵循一条规则：如果读取文件后返回的是满页内容，就应该假定后面还有内容，继续读下去。

一开始，他们把这条规则写在 `read_file` 工具描述中。结果没用。

模型仍然只读第一页，就以为文件已经结束，直接开始回答。

后来，他们没有改一个字，只是把这句话从工具描述移到工具返回结果里。

效果立刻出现了。

因为此时，这条提醒正好紧贴在模型正在阅读的数据旁边。模型刚拿到满页内容，就同时看到“这可能还没读完”的提示，自然会继续调用工具。

**文字没有变，位置变了，行为就变了。**

这就是 Context Engineering 的核心。

不是简单地把更多规则塞给模型，而是要在模型即将犯错的时刻，给它恰好需要的信号。

## Prompt 管“建议”，中间件管“保证”

如果你希望某个行为“大多数时候发生”，Prompt 可能够用。

如果你要求它“每次都必须发生”，那就不要只依赖 Prompt，而应该使用中间件。

中间件可以做两类事情。

### 1\. 用代码处理确定性问题

例如，为模型调用和工具调用设上限，防止无限循环。工具调用出现短暂故障时，自动重试一次。满足特定条件时，强制终止异常运行。

这些都不需要依赖模型“记住规则”。它们是系统层面的保障。

### 2\. 在正确时机注入上下文

LangChain 发现，Nemotron 对“在对话过程中即时插入的指导”响应更稳定。

于是，他们不是把所有规则放在系统提示词中，而是通过中间件分两步引导：先提示 Agent 在行动前制定计划，当计划写完后，再插入一条消息，要求它先复查计划，再开始执行。

从 trace 可以看到，模型会读到这些临时注入的信息，并相应地执行规划和复查。

但相同内容如果只是放在系统提示词中，往往会被模型忽略或弱化。

这也解释了很多实际体验：为什么系统提示词明明写了很多规矩，Agent 还是经常不遵守？因为对模型来说，系统提示词里的长期规则，很容易被后续任务信息、工具结果和对话内容稀释。

关键约束要在关键节点重新出现。

## 哪些“优化”不该保留

不是每个能提升分数的改动，都值得上线。

LangChain 特别强调，要区分两类优化：修复真实行为问题的改动，以及只是在迎合某个评测题目的技巧。

例如，“读取满页文件时继续读取”是通用行为改进。无论面对什么任务，只要出现满页文件读取，都应该继续检查。

但如果某项改动依赖某道评测题中的特殊词汇，或者只对一个固定场景有效，那它即使能提高得分，也很可能只是 benchmark trick。

这种改动会让指标变漂亮，却不会让真实 Agent 更可靠。

对生产环境来说，更有价值的是能迁移到不同任务、不同模型、不同数据上的行为改进。

## Harness 调优也有边界

Harness 能解决很多问题，但不是万能的。

它适合处理的是脚手架层面的失败，例如工具说明写得不清楚、工具结果没有给出足够反馈、上下文没有在正确时间出现、失败后没有重试机制、Agent 缺乏循环保护，以及长上下文压缩策略不合理。

但如果一个问题在各种提示词、中间件、工具描述和上下文策略调整后都没有改善，那么它很可能不在 Harness，而在模型本身。

文章提到，Nemotron 在长程多轮对话中的部分问题没有明显改善。这些问题涉及长任务里持续维护内部状态，更接近模型能力和后训练的范畴。

这时继续加 Prompt 或 Hook，往往只是在强行贴补。正确的方向可能是选择更适合该任务的模型，做面向 Agent 行为的后训练，或者调整任务拆分与系统架构。

## 先找对问题，再决定要不要换模型

这篇文章最重要的价值，不是证明开放模型能接近顶级闭源模型。

而是提供了一个更实用的 Agent 优化思路：**先不要急着怀疑模型不够强，先看 Agent 到底是在哪一步失败。**

如果问题出在脚手架，换模型可能既贵又没必要。

如果问题确实出在模型能力，继续堆提示词也没有意义。

可以用一句话概括：**模型决定能力上限，Harness 决定这些能力有多少能稳定地落到真实任务上。**

对于正在做 Agent 产品的团队来说，不一定要一开始就依赖最昂贵的模型。通过评测驱动的 Harness Engineering，把工具、上下文、流程和保障机制打磨好，很多开放模型也能承担原本需要更贵模型才能完成的工作。

而真正成熟的 Agent 系统，拼的不只是模型性能

更是对任务流程、失败模式、上下文时机和运行机制的理解。
