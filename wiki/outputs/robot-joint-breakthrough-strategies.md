## 一、推动供应商开放调试接口

### 核心思路

不要求供应商交出源码，但要求开放**底层观测和参数配置能力**。这是商业利益和工程需求之间的平衡点。

### 1. 分层开放模型

| 层级 | 名称 | 开放程度 | 内容 |
|------|------|----------|------|
| L3 | 源码级 | 不开放 | FOC 算法源码、保护逻辑 |
| L2 | 参数级 | 选择性开放 | PID 参数在线修改、滤波器系数 |
| L1 | 数据级 | **必须开放** | 电流/速度/位置/温度原始数据 |
| L0 | 状态级 | **必须开放** | 运行状态、错误码、健康度 |

**L0 状态级**：运行状态机（Idle / Ready / Running / Fault）、错误码、温度等级、运行时间。这是最基本的，供应商没有任何理由拒绝。

**L1 数据级**：三相电流、d-q 轴电流、编码器角度/速度、母线电压、PWM 占空比、FOC 观测器输出。这些数据不涉及算法保密，但对客户调试至关重要。

**L2 参数级**：PID 增益、滤波器截止频率、前馈系数、死区补偿值。可以让供应商提供"安全范围"，在范围内允许客户自行调整。

**L3 源码级**：不现实，但可以要求供应商提供算法白皮书，说明使用了什么观测器、什么坐标系变换策略。

### 2. 标准化调试接口定义

在采购合同或技术协议中明确定义：

```
必须提供的调试通道：
- 实时数据流接口（至少 1kHz 输出以下数据）：
  - q 轴电流（给定值 + 反馈值）
  - d 轴电流（给定值 + 反馈值）
  - 电机转速（反馈值）
  - 编码器原始角度
  - 母线电压
  - 芯片温度
  - 驱动器温度

- 参数在线配置接口：
  - 位置环 P/I/D
  - 速度环 P/I/D
  - 电流环 P/I（可选）
  - 滤波器参数（可选）

- 诊断接口：
  - 故障历史（至少记录最近 10 条）
  - 故障时间戳
  - 故障时刻的快照数据（电流、温度、速度）
```

### 3. 商务谈判策略

- **把调试接口写入采购合同**，不是口头约定
- 分阶段开放：先开放 L0 + L1，联调过程中逐步开放 L2
- **绑定付款条件**：调试接口验收通过才付尾款
- 如果供应商完全拒绝，考虑**引入第二供应商**制造竞争压力
- 对于核心关节，考虑**联合开发模式**而非纯采购

### 4. 理想汽车项目实操建议（针对方正关节模组）

- 先在现有基础上，列出**最小必要数据清单**，找方正谈
- 即使只开放串口打印几个关键数据，也比完全黑盒好
- 建立**联合调试机制**：双方工程师坐在一起调试，而不是发邮件来回沟通
- 考虑让方正工程师驻场 1-2 周，集中解决调试问题

## 二、建立标准化的诊断协议

### 核心思路

参考汽车行业的 UDS（ISO 14229）诊断协议，为机器人关节模组建立一套统一的诊断服务规范。

### 1. 诊断服务定义（参考 UDS 0x22 / 0x2E / 0x19 等服务）

| 服务号 | 功能 | 说明 |
|--------|------|------|
| 0x22 | 读数据 | 读取运行时数据（电流/温度） |
| 0x2E | 写数据 | 在线修改 PID 参数 |
| 0x19 | 读 DTC（故障码） | 读取当前和历史故障码 |
| 0x14 | 清除 DTC | 清除故障码记录 |
| 0x27 | 安全访问 | 解锁写参数权限 |
| 0x31 | 例程控制 | 触发自检、校准等例程 |
| 0x34/37 | 下载/上传 | 固件 OTA 升级 |
| 0x85 | 控制 DTC 设置 | 临时屏蔽某些 DTC（调试用） |

### 2. 故障码（DTC）体系设计

**DTC 编码规则：X-YY-ZZ**

- X — 严重程度：1 = 致命（需停机）、2 = 严重（降额运行）、3 = 一般（可继续运行）
- YY — 故障大类：01 = 电机、02 = 编码器、03 = 通信、04 = 温度、05 = 电源
- ZZ — 具体故障号

**示例：**
- `2-01-03` → 严重 — 电机 — q 轴电流偏差过大
- `1-04-01` → 致命 — 温度 — 电机温度超过 150℃
- `3-03-02` → 一般 — 通信 — EtherCAT 通信延迟超过阈值
- `2-02-01` → 严重 — 编码器 — 信号丢失
- `1-05-03` → 致命 — 电源 — 母线过压

### 3. 基于 EtherCAT 的诊断实现

EtherCAT 本身支持 CoE（CANopen over EtherCAT）诊断机制：

| 对象字典地址 | 含义 |
|-------------|------|
| 0x1000 | 设备类型 |
| 0x1001 | 错误寄存器 |
| 0x1003 | 设备状态 |
| 0x1600+ | TxPDO（关节实时数据输出） |
| 0x1A00+ | RxPDO（控制指令输入） |
| 0x1800+ | 制造商自定义对象（扩展诊断数据） |

在对象字典中扩展：
- 实时数据：电流环数据、速度环数据、温度、运行时间
- 配置参数：PID 参数、滤波参数、限幅参数
- 诊断数据：故障计数、累计运行时间、累计扭矩

### 4. 日志系统——关节模组的"黑匣子"

参考汽车行业的 Event Data Recorder：

```
环形缓冲区设计：
- 大小：至少 1000 条记录（约 10 秒 @100Hz）
- 触发条件：故障发生时自动保存
- 每条记录包含：
  - 时间戳（微秒精度）
  - 关节状态机状态
  - 电流数据（三相 + d-q）
  - 速度/位置
  - 温度
  - 控制指令值
  - 错误标志位
- 存储介质：MCU 内部 Flash 或外部 EEPROM
- 读取方式：通过诊断协议下载
```

### 5. 理想汽车项目落地路径

| 阶段 | 周期 | 内容 |
|------|------|------|
| Phase 1 | 1-2 个月 | 和方正协商，在现有关节中增加：通过 EtherCAT/CAN 读取基础运行数据；扩展故障码（至少区分 5-10 种故障类型） |
| Phase 2 | 2-4 个月 | 建立诊断工具链：开发 PC 端诊断上位机；实现 DTC 读取、参数在线配置；实现日志下载和分析 |
| Phase 3 | 4-6 个月 | 完善：环形缓冲区黑匣子功能；OTA 固件升级；批量校准工具 |

## 三、搭建自动化测试台

### 核心思路

建立**单关节台架 → 多关节联调台 → 整机测试**的三级测试体系，把调试从"黑盒摸索"变成"有数据支撑的工程工作"。

### 1. 单关节测试台架

**硬件构成：**
- 关节模组 DUT
- 负载模拟器（磁力粉离合器 / 另一台电机）
- 扭矩传感器（标定级，精度 ±0.5%）
- 高精度编码器（参考级，23bit+）
- 温度传感器 / 红外热像仪
- 电流钳 / 功率分析仪
- 数据采集卡（NI / 自行设计）
- EtherCAT 主站（PC 或工控机）
- CAN 分析仪
- 上位机软件（Python / C#）

**自动化测试用例：**

| 测试项 | 内容 | 验收标准 |
|--------|------|----------|
| 静态电气检查 | 绝缘电阻、对地短路、接线正确性 | 绝缘 > 100MΩ |
| 上电自检 | 编码器自检、通信自检、保护功能 | 上电 2s 内完成 |
| 位置控制精度 | 给定角度 → 等待稳定 → 读取实际角度 | 误差 < 0.1° |
| 速度控制 | 阶跃速度指令，观察响应 | 超调 < 10%，settling < 200ms |
| 扭矩输出精度 | 给定扭矩 vs 扭矩传感器读数 | 误差 < 3% |
| 动态响应 | 正弦波跟踪测试（扫频） | 带宽 > 100Hz |
| 温升测试 | 额定负载运行 30min，记录温度曲线 | 电机 < 120℃，驱动 < 80℃ |
| 故障注入 | 模拟编码器断线、过流、过温 | 保护动作 < 50ms |
| 长期运行 | 连续 24h 跑标准运动序列 | 无异常 |
| 冲击耐受 | 随机冲击测试后功能检查 | 功能正常 |

### 2. 多关节联调台

在单关节测试通过的基础上，把多个关节装到一个**简化机械结构**上（不需要完整机器人躯体）：

- 多关节通信同步性（打同一个指令，各关节响应时间差异）
- 电源分配（所有关节同时满负荷，电压是否 sag）
- 总线负载（EtherCAT/CAN 在满节点时的 CPU 占用和抖动）
- 共振测试（多个关节同时运动时的振动分析）
- 一致性校准（同一指令下各关节的输出一致性）

### 3. 整机测试

最后装到真实机器人上，重点验证：
- 实际负载下的性能（和台架数据对比，识别差距）
- 行走/操作等复合运动的协调性
- 整机功耗和续航
- 长期可靠性（数千次循环）

### 4. 测试数据管理

```
测试数据体系：
├── 原始数据（.csv/.bin）
├── 分析脚本（Python）
│   ├── 计算精度指标
│   ├── 频响分析（FFT）
│   ├── 温升曲线拟合
│   └── 一致性统计
├── 测试报告（自动生成 PDF/HTML）
└── 数据库（记录每次测试结果，追踪趋势）
```

每次测试自动对比：
- 同一关节的批次一致性（台 A vs 台 B）
- 历史趋势（第 1 批 vs 第 5 批，验证供应商质量改进）
- 台架 vs 整机的差异分析

## 四、制定长期技术路线图

### 核心思路

从"纯采购黑盒"逐步走向"联合开发 → 自研核心算法"，建立自主可控的关节驱动技术能力。

### 路线图

**Stage 1：集成能力构建（0-6 个月）**
- 目标：能把供应商关节模组用好
- 建立单关节测试台架
- 定义调试数据接口规范（推动方正开放）
- 建立诊断工具链 v1.0
- 积累调试经验和参数数据库
- 培养 1-2 名关节驱动控制工程师

**Stage 2：联合开发（6-18 个月）**
- 目标：能参与关节模组设计，影响关键技术决策
- 和供应商联合定义下一代关节规格
- 参与 FOC 参数体系设计
- 共同开发诊断 / OTA 功能
- 取得部分源码或算法文档
- 建立联合实验室 / 驻场机制
- 形成标准化文档体系

**Stage 3：核心自研（18-36 个月）**
- 目标：自主掌控关节驱动核心技术
- 自研 FOC 算法（至少核心控制环）
- 自研诊断协议栈（参考 UDS）
- 自研 OTA 升级体系
- 自研关节侧 PCB 和固件架构
- 保留减速器/电机等硬件外采
- 形成可复用的关节驱动平台

**Stage 4：平台化（36 个月+）**
- 目标：关节驱动成为核心竞争力
- 关节驱动平台可跨产品复用
- 支持多种电机类型（BLDC / 有感 FOC / 无感 FOC / 直驱）
- 支持多种通信（EtherCAT / CANFD / TTEthernet）
- 建立功能安全体系（参考 ISO 13849 / IEC 61508）
- 形成专利壁垒
- 甚至可以把关节模组对外输出

### 和汽车领域的对标

理想汽车在电驱领域就走过了类似路径：
1. 早期外采电机和控制器
2. 逐步深入参与设计和调校
3. 最终实现三合一电驱自研

**关节模组完全可以参考这个路径：**
- 电机本身可以继续外采（或定制规格找供应商生产）
- 驱动控制算法、诊断体系、通信协议栈自己掌控
- 这样既避免了重复造轮子（电机绕线、硅钢片冲压），又掌握了核心技术

## 五、优先级建议

按"投入产出比"排序：

| 优先级 | 行动项 | 周期 | 投入 | 收益 |
|--------|--------|------|------|------|
| 🥇 最高 | 推动方正开放 L0 + L1 调试接口 | 1 个月 | 小（商务谈判） | 大（立即改善调试效率） |
| 🥈 高 | 搭建单关节测试台架 | 2 个月 | 中（设备采购） | 大（有数据支撑调试） |
| 🥉 高 | 定义诊断协议框架 | 1 个月 | 小（文档 + 设计） | 中（为后续打基础） |
| 4 | 培养关节驱动工程师 | 持续 | 中 | 大（人才是根本） |
| 5 | 诊断工具链开发 | 3 个月 | 中 | 中 |
| 6 | 启动联合开发讨论 | 6 个月+ | 大 | 大 |
